ExpertCall AI — European Robotic Surgery Market Intelligence

An evidence-grounded AI application for analysing expert-call transcripts and extracting market intelligence from qualitative interview data.

Built as a technical case-study solution for the Hasamex AI Engineer opportunity.

1. Overview

ExpertCall AI analyses expert interviews about robotic surgery adoption across European markets.

The application allows users to:

Analyse 3 expert-call transcripts
Review answers to the provided interview guide
Extract exact supporting quotes
Preserve transcript timestamps
Identify common themes
Compare expert perspectives across markets
Ask natural-language questions across all transcripts
Trace generated answers back to source evidence
Reject questions that cannot be answered from the provided transcripts

The core design principle is:

The LLM is responsible for synthesis, but the transcript remains the source of truth.

Exact quotes, timestamps, expert names, markets and segment IDs are taken from the original transcript records rather than generated by the LLM.

7. How the RAG Pipeline Works

The application uses a retrieval-augmented generation architecture.

Step 1 — Transcript ingestion

Each transcript is parsed into structured segments.

Example:

Expert: Dr. Jean Martin
Role: Head of Urology
Market: France

00:18 Dr. Martin: Adoption is growing...

becomes a structured record:

id: fr_002
expert: Dr. Jean Martin
role: Head of Urology
market: France
speaker: Dr. Martin
timestamp: 00:18
text: Adoption is growing...
Step 2 — Embedding generation

Each expert statement is converted into a vector using:

gemini-embedding-001

Interviewer statements are excluded from the searchable evidence index.

For the provided dataset:

42 total transcript segments
28 searchable expert segments
Step 3 — Vector retrieval

FAISS performs similarity search against the embedded expert statements.

The system retrieves a larger candidate set than ultimately needed.

For example:

User question
     ↓
FAISS
     ↓
15 candidate evidence segments
     ↓
Topic-specific filtering
     ↓
Top 6 evidence segments

This reduces the chance that semantically similar but contextually inappropriate statements reach the LLM.

Step 4 — Evidence filtering

The application detects the type of question.

Examples:

"How important is ROI?"
        ↓
Economics
"What are the barriers?"
        ↓
Barriers
"How long does purchasing take?"
        ↓
Timeline

The corresponding evidence filter is then applied.

This is important because semantic similarity alone does not guarantee that a retrieved segment actually answers the question.

Step 5 — LLM synthesis

Only the selected transcript evidence is supplied to Gemini.

The model is instructed to:

Use only supplied evidence
Avoid external knowledge
Preserve uncertainty
Avoid fabricated statistics
Avoid fabricated quotes
Avoid fabricated timestamps
State when evidence is insufficient
Step 6 — Evidence rendering

The application separately returns the original transcript records.

Therefore:

LLM
 ↓
Generated synthesis

but:

Original transcript
 ↓
Quote
Timestamp
Expert
Market
Segment ID

This separation is a deliberate hallucination-control mechanism.

8. Hallucination Mitigation

Hallucination control is one of the core design requirements of the application.

The system uses several layers.

1. Transcript-only generation

The LLM receives only retrieved transcript evidence.

The prompt explicitly instructs the model not to use external knowledge.

2. Exact quotes are not generated

The LLM is not responsible for creating the displayed evidence quote.

The frontend receives the quote directly from the original TranscriptSegment.

Therefore, an exact quote cannot be accidentally paraphrased or fabricated by the LLM.

3. Timestamps come from source metadata

Timestamps are stored with every transcript segment:

segment_id
timestamp
speaker
expert
market
text

The application displays these original values.

4. Interviewer statements are excluded from retrieval

The FAISS index contains only expert statements.

This prevents questions from being returned as evidence.

5. Topic-specific filtering

Retrieved results are filtered according to the question type.

For example, a future-trend question should prioritize statements such as:

"I expect adoption to continue..."

rather than simply retrieving any segment containing the word "adoption".

6. Unsupported-question detection

Questions requesting information that does not exist in the supplied transcripts are rejected.

For example:

What is the current European robotic surgery market size?

returns:

Not available in the provided transcripts.

rather than allowing the LLM to answer using outside market knowledge.

7. Evidence insufficiency handling

If no relevant evidence survives retrieval and filtering, the system returns:

Not available in the provided transcripts.

This is preferable to generating a plausible but unsupported answer.

11. Important Interpretation Rule

The application distinguishes between:

Evidence

What the expert actually said.

and:

Synthesis

A concise interpretation generated from the supplied evidence.

For example, an expert saying:

"I could see procedure growth above 15 percent annually in some areas."

is treated as an expert expectation, not as an independently verified market forecast.

The application preserves qualifiers such as:

"I expect"
"I think"
"could"
"probably"
"maybe"
"in some areas"

rather than converting them into definitive market facts.

Timestamp accuracy

Did the relevant expert statements appear in the retrieved candidate set?

Does the system refuse questions when the required information is absent?

19. Design Decisions
Why RAG?

The task requires answers to remain grounded in a relatively small collection of source documents.

Retrieval provides the relevant evidence before generation.

Why FAISS?

FAISS provides a lightweight local vector-search implementation that is sufficient for the small case-study dataset and can later be replaced with a persistent vector database.

Why Gemini?

Gemini provides both embedding and generative capabilities while keeping the implementation relatively lightweight for a local case-study application.

Why preserve transcript metadata?

Market intelligence requires traceability.

A generated statement without source context is difficult to audit.

Each segment therefore preserves:

Expert
Role
Market
Speaker
Timestamp
Segment ID
Original text
Why separate synthesis from evidence?

This is the most important reliability decision in the application.

The LLM can summarise evidence, but it should not be trusted to reproduce source metadata perfectly.

Therefore:

LLM → synthesis
Source transcript → citation metadata + exact quote
20. Limitations

This implementation is designed for the provided Hasamex case study and is intentionally lightweight.

Current limitations include:

The demonstration dataset contains three transcripts.
The upload format expects structured .txt transcripts.
The current theme and comparison evidence mappings are designed around the provided case structure.
FAISS is currently used as an in-memory local index.
There is no persistent user database.
There is no authentication layer.
There is no production-scale background ingestion pipeline.
The system does not independently verify expert claims against external sources.
Expert forecasts are treated as interview statements rather than verified market forecasts.

These limitations can be addressed in a production implementation.
